Transport 1

Plain HTTP/1.1 on port 80. No authentication of any kind — every endpoint answers any client that can reach the device. The web UI's login screen is cosmetic: it downloads the credential list from all_dat.get and compares in JavaScript.

1.1  The cache-buster is part of the path, not a query string

xmlHttp.open('GET', 'all_dat.get' + new Date().getTime(), true);

That produces GET /all_dat.get1712345678901 — no ?. The firmware prefix-matches the path. A bare GET /all_dat.get also works. Any emulator or proxy must match the path as a prefix.

1.2  Polling model

The stock UI polls once per second and re-renders only when the full response text differs from the previous one:

if (o != window.myold && index != -1) { …parse… ; window.myold = o; }
setTimeout('httpGetDate()', 1000);

There is no push, no long-poll, no event stream. Twelve consecutive failed polls make the stock UI reload the page.

1.3  Commands are fire-and-forget

POST /video.set returns an empty 200 whether the command was understood, malformed, or out of range. There is no acknowledgement and no error channel. To confirm any change, re-read all_dat.get and compare. Content-Type is ignored by the device — the stock UI sends XHR's default text/plain.

Control commands 2  POST /video.set

2.1  Framing

A request body is one or more commands, each introduced by #, concatenated with no other separator:

#video_d out1 matrix=3#video_d out2 matrix=3#video_d out7 matrix=8
  • Fields within a command are separated by single spaces.
  • Arguments are key=value, except the leading command token and its target.
  • The leading # on the first command is conventional; tolerate its absence.
  • Values are decimal, 1-based, never zero-padded — out8, not out08.
  • Port names are the only free-text values, and they may contain spaces (2.6).

2.2  Command token grammar

The command token reads <group>_<op>, and the last character is the operation:

SuffixMeaningSeen in stock UI
ddata — set / change a valueYes, everywhere
llockNo — inferred from firmware parsing
ssaveNo — inferred from firmware parsing

Only _d is exercised by the stock UI; l and s are unconfirmed. group<N>, port, register<N> and ip do not follow the suffix convention.

2.4  EDID modes

mode selects which table data indexes into, and data is 1-based:

modeTableResponse blockMeaning
0Defaultded1–ded8Built-in preset EDIDs
1Userued1–ued8User-defined EDIDs
2HDMIoed_hdim1–8Copy the EDID of the display on HDMI output data
3HDBToed_hdbt1–8Copy the EDID of the display on HDBT output data

The current assignment for each input is reported back in the E: field, and the resulting EDID string in ied<N>.

2.5  Network configuration

Two shapes are used by the stock UI, both to POST /ip.set: command text as a DHCP toggle (#ip dhcp=0 / #ip dhcp=1), and a conventional urlencoded form POST with fields mac, DHCP, check, ip, sub, gw. A commented-out line in the firmware UI suggests the command form also accepts #ip dhcp=0 ip=<addr> mask=<mask> gw=<addr> — unconfirmed, it is not the path the shipped UI takes.

2.6  Name values

  • Names may contain spaces — #port hdmi2 name=Side Stage TV is one command with a three-word value. A parser that splits the whole command on spaces and reads only the token after name= silently truncates to the first word.
  • Names must not contain ;, : or # — those are response and command delimiters, and the format has no escaping.
  • The stock UI limits entry to 12 characters, but the firmware stores more: a live unit was observed holding Presentation PC 1 (17). The true limit is unconfirmed.
  • Non-ASCII is not supported.

2.7  Batching

Every stock UI "Apply" button batches: it walks its widgets, appends #… for each change, and sends one POST. Batches of 8–24 commands are routine — the audio page always sends all 24. There is no observed size limit.

State response 3  GET /all_dat.get

One line of ASCII. Exactly 160 ;-separated segments, with no trailing separator. Segment position is fixed — the stock UI slices by index, not by key:

var sw_info     = o.split(";").slice(0, 48);     // switch + audio state
    edid_info   = o.split(";").slice(48, 88);    // 5 × 8 EDID entries
var port_name   = o.split(";").slice(88, 112);   // 3 × 8 port names
var source_name = o.split(";").slice(112, 120);  // scene names
var login_info  = o.split(";").slice(120, 136);  // 8 × (user, pass)
var input_info  = o.split(";").slice(136, 144);  // input port status
var hdmi_info   = o.split(";").slice(144, 152);  // HDMI output status
var hdbt_info   = o.split(";").slice(152, 160);  // HDBT output status

3.2  Switch & audio block (0–47)

Six segments repeat for each index i = 1…8. The index means different things in different fields of the same group — the single most misleading part of the format:

FieldIndex refers toMeaning
VO:<o>IN:<i>output oOutput o is sourcing input i. Applies to HDMI output o and HDBT output o alike.
E:<n>M:<mode>D:<slot>input nInput n's EDID assignment: mode 0–3 per 2.4, slot 1–8 within that table.
AI:<n>M:<m>input nAudio source for input n: 0 mute, 1 HDMI embedded, 2 analog.
AO:<o>HDMI:<v>output oHDMI audio-out flag. The stock UI parses this segment and then discards it — it drives no widget. Purpose unconfirmed.
AO:<o>iis:<v>output oAnalog / I²S audio out enabled.
AO:<o>spdif:<v>output oS/PDIF audio out enabled.

"VO:1IN:3".split(":") yields ["VO", "1IN", "3"]; the firmware UI relies on parseInt("1IN", 10) === 1. A regex is clearer and equivalent. VO: is the only routing source of truth — there is no separate HDMI/HDBT routing field, because there is no separate HDMI/HDBT routing.

3.3  EDID blocks (48–87)

All five are human-readable capability summaries, not raw EDID bytes — 3840x2160P60 444 DbV DTS5.1 is resolution/refresh, chroma subsampling, Dolby Vision, audio format.

  • ded1–ded8 — fixed built-in presets, observed identical across units.
  • ued1–ued8 — user slots, writable via edid_d user<N>.
  • ied1–ied8 — the EDID input N is currently presenting to its source. Derived: it resolves E:<n>M:…D:… through the table that mode selects.
  • oed_hdim1–8 and oed_hdbt1–8 — EDID read back from the display on each output.
  • oed_hdim is misspelled in the firmware (hdim, not hdmi). Match it exactly.
  • Unplug in an oed_* field means no display is attached to that output port — a second, independent connection indicator (see 4).

3.4  Port names (88–111)

HDMI output N and HDBT output N have separate names even though they switch as one. The stock UI shows them joined with & on the video page. Empty names are possible; a name is everything after the first : to the next ;.

3.5  Scene names (112–119)

grp1–grp8. The stock UI displays these as tooltips only and provides no way to rename a scene — no rename command for scenes was observed. Whether one exists is unconfirmed.

3.6  Credentials (120–135)

Two consecutive segments share the same key — username first, then password:

lod1:admin;lod1:123456;lod2:admin1;lod2:123456;…lod8:;lod8:;

Eight slots, of which the stock UI only ever uses the first five. Empty slots are lodN:;lodN:;. A key-based parser building a map silently loses the username to the password — read them positionally: even offset = username, odd offset = password.

Security

Every username and password on the device is served in plaintext to any unauthenticated client that can GET /all_dat.get. The login screen is enforced entirely in browser JavaScript against this list. Treat this device as having no access control: it belongs on a management VLAN rather than any network untrusted clients reach, and its credentials should never be reused anywhere else.

3.7  Port status blocks (136–159)

Three blocks of 8 ports. Each port is a comma-separated list of key=value pairs; ports are separated by ; like every other segment, so a block occupies 8 segments and only the first carries the block label:

INPORT:pw5v=1,sig=1,rat=0,col=0,hdcp=0,bit=1;pw5v=1,sig=1,…;…(6 more)…
OUTHDMIPORT:hpd=1,sig=0,rat=0,col=0,hdcp=0,bit=0;hpd=0,…
OUTHDBTPORT:hpd=1,sig=0,rat=0,col=0,hdcp=0,bit=0;hpd=1,…

Consequence: you cannot find port 4's status by looking for a key. Locate the block label, then take the following 8 ;-separated segments in order — 5.1 has a parser.

The stock UI reads exactly two of these fields — input sig and output hpd — and ignores rat, col, hdcp and bit entirely.

Detecting what is actually plugged in 4

This is the part that is easiest to get wrong, and getting it wrong produces exactly one symptom: a UI that reports nothing is connected while pictures are visibly on screen.

siguse — inputs

An input has a source when sig == 1. This is what the stock UI highlights on.

pw5vnever — inputs

Reads 1 on all eight inputs of the captured unit, including ports with nothing plugged in.

hpduse — outputs

An output has a display when hpd == 1. Corroborated by oed_* != "Unplug".

signever — outputs

Reads 0 on output ports that are working normally, including ports driving a live display.

The stock UI highlights an input when sig == 1:

4.3  Recommended test

Rule

output N has a display  ⟺  hpd == 1  OR  oed_* != "Unplug"

hpd and the oed_* EDID readback are independent signals and agree on 15 of 16 ports in the sample. The exception is HDMI output 1 — hpd=1 but oed_hdim1:Unplug — consistent with a cable present whose EDID could not be read, a state worth surfacing differently from "nothing connected" if the UI has room for it.

For a per-logical-output indicator, the way the stock video page shows it, OR the HDMI and HDBT halves. For diagnostics, show them separately: the two halves of one output genuinely differ, and that difference is usually what a technician needs to see.

Parsing recipes 5

5.1  Port status blocks

// Ports 2-8 carry no key, so the block must be read positionally from the raw string.
function parsePortBlock(raw, key) {          // 'INPORT' | 'OUTHDMIPORT' | 'OUTHDBTPORT'
    const at = raw.indexOf(key + ':');
    if (at === -1) return {};
    const ports = {};
    raw.slice(at + key.length + 1).split(';').slice(0, 8).forEach((seg, i) => {
        const fields = {};
        for (const pair of seg.split(',')) {
            const [k, v] = pair.split('=');
            if (k) fields[k.trim()] = parseInt(v, 10);
        }
        ports[i + 1] = fields;               // 1-based port number
    });
    return ports;
}

5.2  Everything else

Split on ; and match each segment by key:

/^VO:(\d+)IN:(\d+)$/          // routing:      [output, input]
/^E:(\d+)M:(\d+)D:(\d+)$/     // input EDID:   [input, mode, slot]
/^AI:(\d+)M:(\d+)$/           // input audio:  [input, mode]
/^AO:(\d+)(HDMI|iis|spdif):(\d+)$/
/^port_i(\d+):(.*)$/          // input name
/^port_ohdmi(\d+):(.*)$/      // HDMI output name
/^port_ohdbt(\d+):(.*)$/      // HDBT output name
/^grp(\d+):(.*)$/             // scene name
/^oed_hdim(\d+):(.*)$/        // HDMI sink EDID — note the firmware's misspelling
/^oed_hdbt(\d+):(.*)$/        // HDBT sink EDID

Use (.*), not (.+), for name and EDID fields: empty values occur.

5.3  Change detection

Compare the whole raw response string against the previous one before re-parsing, as the stock UI does. A 1 Hz poll of a 3.3 KB string is cheap; re-rendering on every poll is not.

Gotchas checklist 6

  1. oed_hdim is misspelled in the firmware. Preserve it exactly.
  2. Status blocks are positional — only the first of 8 ports carries the block label.
  3. lod<N> appears twice per user — username, then password.
  4. The response has no trailing ; — it splits into exactly 160 segments, not 161.
  5. The cache-buster is glued to the path, with no ?.
  6. Index meaning changes within a group — VO:/AO: are output-indexed, E:/AI: input-indexed, in the same repeating six segments.
  7. HDMI and HDBT outputs switch as one but have separate names, EDIDs and connection status.
  8. register<N> is 0-based; every other index in the API is 1-based.
  9. Port names may contain spaces — don't split the command on whitespace and read one token.
  10. Commands are never acknowledged — poll to confirm.
  11. pw5v (inputs) and sig (outputs) are the wrong connection fields.
  12. No authentication anywhere, and credentials sit in the state response in plaintext.
